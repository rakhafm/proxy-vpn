Masalah

Crawler pricing engine mengambil halaman listing OLX. OLX memakai Akamai Bot Manager yang memblokir per alamat IP, dan reputasi sebuah IP bergeser dalam hitungan jam. Akibatnya tidak ada daftar exit yang bisa ditulis sekali lalu dipakai selamanya — daftarnya harus diperiksa terus dan dipangkas sendiri.

Keadaan sekarang semuanya manual:

  • Dua exit hidup di namespace crawler-prod: vpn-pia (AS137409 GSL Networks) dan vpn-proton (AS212238 Datacamp).
  • Daftar proxy tinggal di file/proxies.txt pada PVC crawler-prod-pvc-fs (CephFS, RWX), diisi tangan.
  • Tidak ada yang memeriksa apakah sebuah exit masih bisa membuka OLX. Healthcheck gluetun hanya menguji tunnel-nya hidup, bukan apakah OLX menerimanya.
  • Tidak ada riwayat, tidak ada notifikasi, tidak ada cara memantau selain SSH.
Yang sudah benar dan dipertahankan

getconfig() di config/scrape.py:208 membaca proxies.txt setiap kali dipanggil, bukan sekali saat pod start. Jadi mengganti isi file itu langsung berlaku tanpa restart worker. Mekanisme penyebaran daftar sudah ada — yang belum ada adalah yang mengisinya.

Bukti terukur

Semua angka di bawah hasil pengujian 19 Agustus 2026, bukan asumsi. Ini yang membentuk desainnya.

node-vn-01.protonvpn.net dijalankan tiga kali berturut-turut: entry endpoint berganti, exit IP konsisten — tapi berbeda dari yang tercatat empat jam sebelumnya.

Stabil dalam hitungan menit, bergeser dalam hitungan jam. Menyimpan “profil yang lolos” lalu memakainya besok tidak menjamin apa pun — yang tersimpan cuma nama, dan nama itu menunjuk IP lain nanti. Karena itu sistem ini menyimpan verdict tentang slot yang sedang berjalan, bukan daftar nama server favorit.

Beberapa hostname berbagi satu exit IP

Pada sapuan yang sama, lima hostname — node-sg-34, node-sg-38, node-sg-42, node-th-01, node-vn-01 — semuanya keluar dari 159.26.115.123. Proton memakai NAT keluar bersama, dan sebagian lokasi (Thailand, Vietnam) dilayani hub Singapura. Artinya memilih “tiga profil berbeda” bisa berarti satu exit IP. Sistem wajib men-dedupe pada exit IP, bukan pada nama server.

IP yang bersih pun menjawab curl dengan interstitial 2.2 KB dan 0/5 marker — sama seperti IP yang diblokir. Jadi curl cukup untuk memastikan sesuatu buruk, tapi vonis bersih butuh browser sungguhan. Pembagian job harian/per-jam di PRD ini mengikuti pembagian itu.

Marker yang dipakai adalah OLX_SEARCH_MARKERS dari utility/utility.py:76 — kriteria yang sama dipakai pipeline produksi, sudah diverifikasi cocok dengan HTML yang divonis lolos. Probe dan crawler tidak akan berbeda pendapat.

Tujuan

  • Menjaga minimal 3 exit hidup yang terbukti bisa membuka OLX, lintas dua provider agar ASN-nya tidak tunggal.
  • Mengeluarkan exit yang diblokir dari daftar dalam ≤1 jam tanpa campur tangan manusia.
  • Menyajikan daftar yang masih hidup lewat satu URL yang bisa dipakai layanan mana pun.
  • Halaman pantau: keadaan tiap slot, exit IP, riwayat probe, kapan terakhir lolos.
  • Tidak butuh perubahan kode di crawler.

Bukan tujuan

  • Menembus atau menyelesaikan tantangan bot Akamai. Sistem ini memilih exit yang tidak diblokir, bukan melewati pemblokiran.
  • Menaikkan laju crawl. Tujuannya mengurangi permintaan yang gagal, bukan menambah jumlah permintaan.
  • Mengganti jalur file proxies.txt. Jalur itu tetap jadi cara crawler membaca daftar.
  • Autentikasi berlapis atau multi-tenant. Ini alat internal satu tim.

Garis tebal membawa trafik nyata; garis putus-putus adalah kendali. Manager tidak pernah menyentuh trafik crawler — ia hanya menyalakan, menguji, dan mematikan slot, lalu menerbitkan daftarnya.

Manager memegang tiga tanggung jawab yang sengaja tidak dipecah jadi layanan terpisah, karena ketiganya berbagi satu state dan memecahnya hanya menambah cara untuk tidak sinkron:

  • Orkestrator — menyalakan dan mematikan container gluetun lewat Docker.
  • Prober — menjalankan uji OLX dan menuliskan verdict.
  • Penerbit — API dan halaman pantau di atas state yang sama.

Probe harian berjalan di image sendiri, bukan image crawler

Koreksi dari rancangan awal — dua kali

Koreksi pertama (masih benar): jalur OLX crawler yang sebenarnya adalah scrapeselenium() di config/scrape.py:101 — Selenium + Chrome, opsi dari _chrome_options() (--proxy-server, UA dari agent.txt, --headless=new, --disable-blink-features=AutomationControlled). Bukan Playwright, dan bukan probe.js (Node + Playwright) yang dipakai menyapu — fingerprint keduanya berbeda dari crawler produksi.

Koreksi kedua, ketemu waktu implementasi: rancangan awal saya menjalankan probe di dalam image crawler produksi (`harbor.aslcode.dev/...`) supaya Chrome-nya identik. Itu ternyata berlebihan — yang benar-benar perlu identik cuma opsi launch Chrome dan kriteria vonisnya, bukan seluruh image crawler (yang juga membawa Selenium, dependensi scraping lain, dan butuh login registry Harbor). Sekarang probe jalan di image sendiri (pool/probe/) yang isinya cuma Chrome + chromedriver + dua fungsi yang disalin tertulis dari repo crawler (_chrome_options(), olx_search_markers() — lihat sitasi baris asal di komentar pool/probe/olx_probe.py). Efeknya: VM tidak perlu kredensial registry apa pun, dan build/rilis image crawler tidak lagi mempengaruhi probe.

Probe harian dijalankan begini (lihat pool/probes.py):

docker run --rm --network host \
  -e PROXIES="http://127.0.0.1:9001" \
  -v pool/probe/olx_probe.py:/app/olx_probe.py:ro \
  -v pool/probe-out:/out \
  olx-pool-probe:latest \
  python3 olx_probe.py

Script probe-nya di-mount, bukan dibangun ke dalam image — mengubah logika vonis tidak perlu docker build ulang. HTML + screenshot yang dirender ikut disimpan ke pool/probe-out/ lewat mount kedua — bukti nyata untuk tiap probe, dipangkas otomatis lewat PROBE_OUT_RETAIN_DAYS supaya tidak numpuk tak terbatas di disk VM.

Efek sampingnya tetap seperti rancangan awal: Chrome, chromedriver, dan Selenium tidak perlu dipasang di VM sama sekali — cuma Docker dan Python. --network host dipakai supaya container probe bisa menjangkau slot di 127.0.0.1:9001. Bedanya, Chrome-nya sekarang disalin instalasinya dari Dockerfile crawler (bukan meminjam image-nya) — kalau versi Chrome di image crawler berubah, itu tidak otomatis mengikuti di sini, harus disinkronkan manual. Trade-off yang sadar diambil untuk melepas ketergantungan Harbor.

Model slot

Abstraksi intinya adalah slot: identitas tetap dengan port tetap, yang isinya boleh berganti. Konsumen memakai http://pool-host:9001 dan URL itu tidak pernah berubah walau server VPN di belakangnya dirotasi tiap hari.

Ini alasan yang sama dengan catatan di manifest k8s yang sudah ada — satu Deployment per exit, bukan replicas — tapi dipakai untuk masalah yang berbeda: di sana supaya pemilihan acak getconfig() benar-benar berarti IP berbeda, di sini supaya rotasi tidak mengubah alamat yang sudah dipegang konsumen.

SQLite cukup — beban tulisnya beberapa baris per jam.

Job harian & per jam

Rotasi harian — 03:00 Asia/Jakarta

Mengganti isi tiap slot dan memastikan yang terpasang benar-benar bisa membuka OLX.

  1. Segarkan daftar kandidat dari gluetun format-servers (tanpa login).
  2. Untuk tiap slot: ambil kandidat berikutnya, jalankan gluetun, tunggu healthy.
  3. Ukur exit IP. Kalau sudah dipakai slot lain, buang — lanjut kandidat berikutnya.
  4. Probe browser: harus mencapai 1.6 MB dan ≥1 marker pipeline.
  5. Lolos → active. Gagal → coba kandidat berikutnya, maksimal 5 percobaan per slot.
  6. Slot yang tetap gagal ditandai dead dan tidak diterbitkan.

Verifikasi per jam

Hanya memastikan yang sedang berjalan masih lolos. Tidak mengganti profil, sesuai rancangan.

  1. Untuk tiap slot active: probe curl murah.
  2. Ketemu id="referenceNum" → tandai blocked, keluarkan dari daftar terbit.
  3. Interstitial bm-verify → dianggap masih hidup; itu jawaban normal untuk curl.
  4. Tunnel tidak menjawab sama sekali → connecting, dicoba lagi jam berikutnya.
Lubang yang sengaja dibiarkan terbuka

Karena job per jam hanya mengeluarkan dan tidak pernah mengisi, jumlah slot hidup hanya bisa turun sepanjang hari. Kalau tiga slot terblokir jam 14:00, kolam tinggal nol sampai rotasi jam 03:00 besok.

Ini konsekuensi dari “per jam tanpa mengganti profil”. Mitigasinya sebuah flag HOURLY_REFILL yang default mati agar sesuai rancangan; kalau dinyalakan, slot yang baru diblokir langsung dirotasi saat itu juga — hanya slot itu, tidak menyentuh yang lain. Saya sarankan menyalakannya setelah rotasi harian terbukti stabil.

Keputusan: kolam kosong menjawab 503, bukan 200

Kalau tidak ada slot hidup, GET /proxies membalas 503 dengan badan kosong — bukan 200 dengan daftar kosong. Alasannya ada di bagian berikut, dan ini pembeda antara sistem yang gagal dengan aman dan sistem yang gagal diam-diam.

Integrasi konsumen

Crawler tidak mengambil URL — getconfig() membaca env PROXIES atau file assets/file/proxies.txt. Jadi jembatannya satu CronJob kecil, dan tidak ada kode crawler yang berubah: 

curl -fsS "$POOL_URL/proxies" -o /tmp/p \
  && [ -s /tmp/p ] \
  && cp /tmp/p /app/assets/file/proxies.txt

Tiga pengaman dalam satu baris itu, dan semuanya penting:

  • -f — gagal saat manager membalas 503, jadi file lama dibiarkan utuh.
  • -s /tmp/p — menolak menulis file kosong.
  • cp ke PVC — worker memungutnya pada panggilan getconfig() berikutnya, tanpa restart.
Kenapa file kosong berbahaya

proxies.txt kosong membuat len(PROXIESS) > 0 bernilai false, dan getconfig() mengembalikan None — worker lanjut crawl tanpa proxy, langsung dari IP egress cluster. Itu justru IP yang paling tidak boleh terekspos ke OLX, dan kegagalannya senyap: tidak ada error, crawl tetap jalan, sampai IP cluster yang kena blokir.

Alternatifnya mengubah scrape.py agar mengambil URL langsung. Saya tidak menyarankannya: itu menjadikan manager sebagai dependensi runtime tiap permintaan crawl, sedangkan pola file di atas membuat manager mati hanya berarti daftarnya berhenti disegarkan.

Penempatan

Manager dan seluruh slot gluetun berjalan di VM Ubuntu yang satu network dengan node k8s. Ini menghapus penghalang terbesar rancangan berbasis Docker: pod bisa menjangkau slot langsung lewat IP, tanpa Service, Ingress, atau NodePort.

Terukur langsung: 1.9 GB RAM tanpa swap sama sekali, dan 9.2 GB disk dengan ~3.9 GB tersisa. Tabel Kapasitas di bawah menghitung kebutuhan 6 slot penuh berdasarkan batas atas limit manifest k8s (~2 GB) — pas-pasan untuk RAM sekecil ini, apalagi tanpa jaring pengaman swap. Karena itu Fase 3 dimulai dari 3 slot (2 PIA + 1 Proton), bukan 6 — lihat pool/deploy/README.md.

Aturan firewall

Trafik dari pod ke alamat di luar cluster CIDR biasanya di-SNAT menjadi IP node oleh Canal, jadi VM akan melihat koneksi datang dari 10.0.0.21–24 — bukan dari 10.42.x.x. Tapi perilaku itu bergantung konfigurasi ipMasq, jadi izinkan keduanya dan tidak perlu menebak: 

ufw allow from 10.0.0.0/24  to any port 8080      proto tcp   # API + halaman pantau
ufw allow from 10.0.0.0/24  to any port 9001:9006 proto tcp   # slot proxy
ufw allow from 10.42.0.0/16 to any port 8080      proto tcp
ufw allow from 10.42.0.0/16 to any port 9001:9006 proto tcp
Jangan pernah ekspos port ini ke internet

Port 9001–9006 adalah proxy HTTP terbuka tanpa autentikasi. Terjangkau dari internet, keduanya langsung jadi relay terbuka yang dipakai orang lain — bandwidth VPN kamu terpakai pihak asing, dan exit IP-nya ikut terbakar reputasinya oleh trafik yang bukan milikmu. Batasi ke 10.0.0.0/24 dan 10.42.0.0/16 saja, jangan berikan aturan ufw allow 9001 tanpa klausa from.
